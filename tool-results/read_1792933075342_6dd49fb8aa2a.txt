    82→    82→### 2.2 Jumlah subcarrier & format data (semua [DIVERIFIKASI] dari tabel IDF v5.4)
    83→    83→
    84→    84→Tabel resmi ESP32-S3 (S3 = non-HE path) untuk kombinasi kanal/paket:
    85→    85→
    86→    86→| Kondisi | Subcarrier indeks | Total byte `len` |
    87→    87→|---|---|---|
    88→    88→| 20 MHz, non-HT, non-STBC (LLTF) | 0~31, −32~−1 = **64 pasang I/Q** | **128** |
    89→    89→| 20 MHz, HT, non-STBC (LLTF + HT-LTF) | masing-masing 64 pasang | **256** |
    90→    90→| 20 MHz, HT, STBC (+STBC-HT-LTF) | — | **384** |
    91→    91→| 40 MHz (secondary above/below), HT | 0~63 / −64~−1 per LTF | hingga **612** |
    92→    92→
    93→    93→Tabel subcarrier PHY (IDF v5.4, seksi CSI):
    94→    94→- 802.11a/g: −26..+26, pilot −21/−7/+7/+21 → **52 total, 48 data usable**
    95→    95→- **802.11n 20 MHz (HT20): −28..+28 → 56 total, 52 data usable** (pilot −21/−7/+7/+21)
    96→    96→- 802.11n 40 MHz (HT40): −57..+57 → **114 total, 108 data usable** (6 pilot)
    97→    97→
    98→    98→Jadi: buffer CSI ESP32-S3 HT20 = hingga **64 pasang I/Q per LTF** (2 byte per pasang, imajiner dulu lalu riil; LLTF+HT-LTF = 256 byte), sedangkan **jumlah subcarrier fisik 802.11n HT20 = 56 (52 data)** — dua angka yang berbeda makna dan sering tertukar di literatur. RuView memakai "64 subcarriers, ~5 KB/s @ 20 Hz" di README firmware dan "56 subcarriers" di ADR-018 — keduanya konsisten dengan tabel di atas (buffer vs grid fisik). Keterangan pertama `first_word_invalid` (4 byte pertama tak valid karena batasan HW S3) terdokumentasi di IDF dan disanitasi RuView (bit 5 byte 19 ADR-018).

   100→   100→### 2.3 esp-csi (github.com/espressif/esp-csi) (semua [DIVERIFIKASI], master diunduh 2026-10-25)
   101→   101→
   102→   102→- README: "**Full series support: All ESP32 series support CSI, including ESP32 / ESP32-S2 / ESP32-C3 / ESP32-S3 / ESP32-C5 / ESP32-C6 / ESP32-C61**." → **ESP32-S3 didukung penuh**.
   103→   103→- Tiga pola perolehan CSI di README:
   104→   104→  1. **csi_recv_router** — ESP32 STA terhubung ke router, ping gateway → CSI dari balasan router (contoh mendukung ESP32/S2/C3/**S3**/C5/C6/C61 per README-nya; ping `1000/CONFIG_SEND_FREQUENCY` ms; catatan kode: "only LLTF sub-carriers are selected" demi kompatibilitas router).
   105→   105→  2. **CSI antar-perangkat** (dua ESP32 sama-sama ping router; A mendengar ping B).
   106→   106→  3. **csi_send + csi_recv** — pengirim khusus: `csi_send` mengirim **ESP-NOW broadcast** (peer FF:FF:FF:FF:FF:FF, `ifidx = WIFI_IF_STA`, kanal `CONFIG_LESS_INTERFERENCE_CHANNEL`, `esp_wifi_set_channel()` manual, laju `CONFIG_SEND_FREQUENCY` Hz; HT20 atau HT40 dengan secondary-below; `esp_now_set_peer_rate_config` mengatur phymode/rate) dan penerima `csi_recv` (WIFI_MODE_STA, tidak terhubung AP, konfigurasi `acquire_csi_ht20/ht40`, callback CSI). Inilah pola "TX ESP-NOW → RX collector".
   107→   107→- Contoh aplikasi **esp-radar** (console_test, wifi_sensing_demo) di dalam esp-csi: "Supported Targets | ESP32 | ESP32-C3 | ESP32-C5 | ESP32-C6 | ESP32-C61 | ESP32-S2 | **ESP32-S3**" — deteksi kehadiran/gerak on-device dengan kalibrasi.

   118→   118→### 2.5 Bukti kode RuView (klon lokal commit `fefb0f9`) (semua [DIVERIFIKASI], path:baris)
   119→   119→
   120→   120→- `firmware/esp32-csi-node/main/csi_collector.c:98` — `#define CSI_MIN_SEND_INTERVAL_US (20 * 1000)` dengan komentar "Default: 20 ms = **50 Hz max send rate**" (pelindung buffer lwIP dari ENOMEM).

   123→   123→- `csi_collector.c:678-691` — konfigurasi S3 (non-HE): `lltf_en`, `htltf_en`, `stbc_htltf2_en`, `ltf_merge_en` → `esp_wifi_set_csi_config` + `esp_wifi_set_csi_rx_cb` + `esp_wifi_set_csi(true)`.

MGMT-only gives ~10 Hz (beacons)"; `csi_collector_enable_data_capture()` (baris ~846: filter MGMT+DATA) dipakai untuk papan tanpa layar.
   125→   125→- `csi_collector.c:705-708` + `496-539` — **self-ping ke gateway** sebagai sumber lantutan OFDM unicast (meniru `csi_recv_router` esp-csi; komentar "Mirrors Espressif's esp-csi csi_recv_router reference"); catatan #2287: sebagian AP membalas ping pada rate 802.11b DSSS yang **tidak menghasilkan CSI**.
   126→   126→- `csi_collector.c:422` — "At **10 Hz observed CSI rate**" pada bench ADR-110 (laju CSI riil bergantung lalu lintas).
   127→   127→- `csi_collector.h:24` — `CSI_MAX_FRAME_SIZE = 20 + 4*256*2` (header 20 B + maksimum 4 antena × 256 subcarrier × 2 B).
   128→   128→- README firmware: Tier 0 "~20 Hz per channel, ~5 KB/s per node (64 subcarriers, 1 antenna)"; "On S3, STBC frames can carry **192 I/Q entries**; edge processing uses the first 128 entries" (isu #2286).
   129→   129→- ADR-018 (`docs/adr/ADR-018-esp32-dev-implementation.md`): "For 3 antennas, 56 subcarriers: 20 + 336 = 356 bytes per frame"; "~100 Hz at 56 subcarriers = ~35 KB/s per node"; "Most ESP32-S3-DevKitC boards have one on-board antenna"; **"No on-device FFT"** — agregator Rust yang mengekstraksi fitur (rujuk ADR-012 vs ADR-018).

   183→   183→## 4. KOEKSISTENSI RADIO: CSI + STA-TCP/IP + ESP-NOW pada SATU ESP32-S3 (Pertanyaan 4 — paling kritis)
   184→   184→
   185→   185→### 4.1 Jawaban singkat
   186→   186→
   187→   187→**[DIVERIFIKASI — bukti kode produksi] YA untuk kombinasi (STA terhubung AP + UDP/TCP ke server + penangkapan CSI promiscuous dari semua paket yang didengar) — persis arsitektur firmware RuView esp32-csi-node yang berjalan di ESP32-S3.** **[DIVERIFIKASI — bukti kode + komentar] YA untuk ESP-NOW bersamaan dengan STA terhubung** (dipakai RuView untuk time-sync lintas node "Works on both S3 and C6"; dokumentasi ESP-NOW mengizinkan pengiriman lewat antarmuka Station). **BUTIR PENTING: semua aktivitas harus pada KANAL YANG SAMA** (kanal AP tempat STA terhubung); node ESP-NOW pengirim harus set kanal yang sama. Lalu lintas TX node lain yang berada pada kanal berbeda TIDAK akan menghasilkan CSI di penerima.
   188→   188→
   189→   189→### 4.2 Bukti per skenario
   190→   190→
   191→   191→**Skenario A — satu S3 menangkap CSI dari paket node lain SAMBIL terhubung STA & mengirim UDP ke server [DIVERIFIKASI]:**
   192→   192→- RuView `main.c:189-267` `wifi_init_sta()`: `WIFI_MODE_STA`, tunggu `IP_EVENT_STA_GOT_IP` (baris 256-266).
   193→   193→- Setelah terhubung, `csi_collector.c:637-650`: `esp_wifi_set_promiscuous(true)` + filter → callback CSI menyala untuk **semua frame yang didengar** (beacon AP, frame node lain, ping reply), dengan MAC filter opsional (`csi_collector.c:343-350`, ADR-060).
   194→   194→- CSI lalu dikirim via UDP oleh `stream_sender.c:48,105` (`SOCK_DGRAM`/`sendto`) ke server — jadi radio yang sama menangkap CSI dan mengalirkan data IP.
   195→   195→- Dokumentasi ESP-IDF v5.4 mendukung pola ini secara eksplisit (rekomendasi sniffer mode di §2.1) dan datasheet menyatakan STA+SoftAP koeksisten pada MAC (§1.3).
   196→   196→- esp-csi `csi_recv_router` (mendukung S3) adalah contoh resmi sejenis: STA terhubung router + ping + CSI.
   197→   197→
   198→   198→**Skenario B — ESP-NOW + STA terhubung pada satu chip [DIVERIFIKASI]:**
   199→   199→- RuView `main.c:554-566`: komentar kode "ADR-110 D1 workaround: **ESP-NOW cross-node sync. Initialized after WiFi STA connects** (ESP-NOW needs the WiFi driver up). **Works on both S3 and C6**". `c6_sync_espnow.c:33` — beacon broadcast **setiap 100 ms** (10 Hz), payload 16 byte, MAC broadcast FF:FF:FF:FF:FF:FF; dipakai untuk sinkronisasi epoch lintas node (presisi ~490–540 µA-level µs terukur di ADR-110 §A0.7–A0.10, dikutip komentar kode).
   200→   200→- Dokumentasi ESP-NOW (esp_now.rst, IDF master, diunduh 2026-10-25): "ESP-NOW data must be transmitted after Wi-Fi is started … **You can send ESP-NOW data via both the Station and the SoftAP interface**"; "If the channel is set to 0, data will be sent on the current channel. **Otherwise, the channel must be set as the channel that the local device is on**" → batasan kanal tunggal.
   201→   201→- esp-csi `csi_send`: contoh resmi TX ESP-NOW (peer channel = kanal tetap) yang oleh penerima (`csi_recv`, STA tidak terhubung) menghasilkan CSI — kombinasi TX-ESP-NOW→RX-CSI terdokumentasi resmi.
   202→   202→
   203→   203→**Skenario C — alternatif bila koeksistensi penuh dirasa berisiko [keputusan desain, bukan keharusan]:**
   204→   204→- **Dua peran terpisah** (node CSI khusus + node gateway WiFi) — didukung arsitektur RuView (mesh 3–6 node, TDM slot, `rv_mesh.c`), tetapi MENAMBAH perangkat; bukti kode menunjukkan tidak diperlukan untuk kasus 2–3 modul pada satu AP.
   205→   205→- **Time-slicing / duty-cycle** — RuView punya `power_mgmt.c` (light-sleep duty cycling NVS `power_duty`) tetapi **modem-sleep mematikan CSI**; duty-cycling CSI = celah deteksi (angka laju 50 Hz maksimum akan turun). [DIVERIFIKASI adanya power_mgmt; implikasi = analisis]
   206→   206→- **ESP-NOW untuk hasil label antar modul** (bukan lewat AP) — dimungkinkan (payload ≤250 B cukup untuk label+timestamp), dengan catatan kanal sama dan throughput 1 Mbps default.
   207→   207→
   208→   208→### 4.3 Batasan/risiko koeksistensi yang terdokumentasi (semua [DIVERIFIKASI])
   209→   209→
   210→   210→1. **Kanal tunggal**: STA terhubung → terkunci kanal AP; semua TX node lain harus di kanal itu untuk menghasilkan CSI. RuView: auto-detect kanal AP (`csi_collector.c:605-614`) + MAC filter. ADR-029 channel-hop (tabel hop 1/6/11, dwell 50 ms) BERTENTANGAN dengan STA terhubung (hop akan memutus asosiasi) — di RuView, hop hanya aktif `hop_count>1` dan mode default single-channel; dokumentasi csi_send juga bekerja tanpa AP.
   211→   211→2. **Beban interrupt**: filter DATA penuh memicu 100–500+ interrupt/s yang bisa **crash Core 0** (race cache SPI flash di blob Wi-Fi; RuView#396) — RuView memilih MGMT-only pada papan berlayar, MGMT+DATA pada papan tanpa layar, plus gate 50 Hz. → untuk modul berlayar (skripsi ini), ikuti pola MGMT-only + sumber trafik terkendali.
   212→   212→3. **Modem-sleep harus mati** (`WIFI_PS_NONE`) untuk CSI andal (`csi_collector.c:619-632`; RuView#521) → konsekuensi daya §5 dan peringatan termal RuView untuk papan mungil.
   213→   213→4. **AP yang membalas ping pada rate 802.11b tidak menghasilkan CSI** (#2287) — solusi RuView: host LAN mengirim UDP `csi-udp-poke.py` 50 Hz ke node.
   214→   214→5. **Streaming audio I2S + CSI pada radio yang sama** (rencana modul penerjemah dengan mikrofon): belum ada bukti di RuView (audio bukan fitur RuView). Wi-Fi STA ~20 Mbps TCP kapasitas (IDF) secara teoretis cukup untuk Opus/PCM terkompresi, tetapi **interaksi beban TX audio dengan laju CSI belum teruji** → risiko terbuka untuk diuji T0.    251→   251→## 6. Komunikasi antarmodul — ESP-NOW & alternatif (Pertanyaan 6)
   252→   252→
   253→   253→Semua [DIVERIFIKASI] dari `esp_now.rst` (IDF master, diunduh 2026-10-25) + IDF v5.4 S3 Wi-Fi guide kecuali diberi label lain:
   254→   254→
   255→   255→- **Payload maksimum**: v1.0 = **250 byte** (`ESP_NOW_MAX_DATA_LEN`); **v2.0 = 1470 byte** (`ESP_NOW_MAX_DATA_LEN_V2`, perangkat v2 bisa terima keduanya; v1 hanya terima ≤250 B dari v2, selebihnya dipotong/dibuang). → label isyarat + timestamp + confidence (+ frasa pendek) muat di 250 B.
   256→   256→- **Rate default 1 Mbps**; rate/phymode per-peer bisa diatur (`esp_now_set_peer_rate_config` — dipakai esp-csi csi_send untuk menjamin rate OFDM tertentu demi kualitas CSI).
   257→   257→- **Keamanan**: CCMP; PMK + LMK 16 byte; multicast tidak dienkripsi; **maks 20 perangkat peer** (17 terenkripsi, default 7) di ESP32/S3.
   258→   258→- **Kanal**: peer channel 0 = kanal lokal saat ini; selain itu **harus sama dengan kanal lokal** (batasan utama untuk koeksistensi dengan STA, lihat §4.3).
   259→   259→- **Latensi**: ESP-NOW connectionless satu hop MAC — tidak ada angka latensi resmi di dokumen [TIDAK DITEMUKAN angka resmi]; pengukuran komunitas umumnya milidetik-level (tidak dikutip sebagai fakta). → latensi antarmodul harus diukur T0. RuView memakai beacon 10 Hz dengan stdev offset ~540 µs (ADR-110 §A0.8, dikutip kode) — indikasi latensi propagasi+software rendah.
   260→   260→- **Jarak praktis**: dokumen resmi hanya menyebut mode **Long Range hingga 1 km** (IDF v5.4 S3 Wi-Fi feature list). Jarak mode normal [TIDAK DITEMUKAN angka resmi] — bergantung antena/lingkungan; untuk ruang kelas (≤10 m) bukan risiko.
   261→   261→- **Alternatif**: (a) via AP server (TCP/UDP, sudah berjalan di jalur RuView); (b) WiFi Direct / SoftAP — didukung chip (STA+SoftAP), dipakai esp32-csi-tool `active_ap`; (c) ESP-NOW — paling sederhana untuk label ringan antar modul pada kanal sama.

   265→   265→## 7. Kontradiksi & ketidakpastian yang ditemukan
   266→   266→
   267→   267→1. **"esp32-csi-tool ada di organisasi espressif"** (dugaan tugas) vs **kenyataan**: repo hanya ada di `StevenMHernandez/ESP32-CSI-Tool`; path espressif 404. → perbaiki rujukan proposal bila perlu.
   268→   268→2. **"TX-nya ESP-NOW" pada esp32-csi-tool** vs kode master: TX-nya UDP socket (active_sta); **ESP-NOW dipakai esp-csi csi_send** dan RuView sync. Dua klaim ini sering dicampur dalam literatur — kutip dengan hati-hati.
   269→   269→3. **Angka "56 subcarrier" vs "64 pasang I/Q"**: keduanya benar pada konteks berbeda (grid fisik 802.11n HT20 = 56 total/52 data vs buffer CSI per LTF = 64 pasang). ADR-018 RuView memakai 56 (3 antena hipotetis), README firmware memakai 64. Proposal sebaiknya menyatakan definisi eksplisit.
   270→   270→4. **Laju CSI**: klaim "hingga 100 Hz" (ADR-018, teoretis) vs gate 50 Hz (kode) vs laju teramati 10–20 Hz (komentar kode & README) — gunakan "hingga 50 frame/s (gate firmware), 10–20 Hz tipikal" di proposal.
   271→   271→5. **Ukuran model "hingga 16 MB PSRAM"**: benar di level chip (ESP32-S3R16V) tetapi varian EOL/1,8 V; modul umum dipasaran 8 MB octal — jangan menjanjikan 16 MB.
